Two slide-ready takeaways:

    pure-4DGS freeze, ~10x better than constant velocity. (Figure: z-vs-time

  - Small ball: the naive boundary extrapolators BLOW UP (const-vel 20.8 cm,

5. ANALYSIS / INSIGHTS SLIDE (directly targets the Robustness criterion)
--------------------------------------------------------------------------------
What works:
  - Opacity-weighted centroid from the Wu 4DGS gives a clean trajectory inside
    the train window.
  - Decoupling reconstruction from prediction (extract -> fit closed-form physics
    -> roll forward) is robust: Steps 4b/4c are pure NumPy/scipy, backend-agnostic,
    and the constant 4DGS-vs-PyBullet world-frame offset cancels out in pose deltas.
  - Multi-view evaluation: we render/score all 12 cameras (added per-camera
    intrinsics so cameras with different FoV project correctly). Evaluating more
    POVs is NOT leakage — the prediction is a single camera-independent 3D point;
    cameras are only projection targets. The held-out axis that matters is TIME.

What doesn't (yet):
  - x/y "wobble" in the extracted trajectory: the 4DGS used here was a 5k-iteration
    debug run; the non-rigid deformation introduces small lateral jitter. Robust
    centroid estimators (median/trim) reduce but don't fully remove it. Root-cause
    fix = train 4DGS longer (30k).
  - Render appearance: real Gaussian compositing not yet run end-to-end (needs a
    background 3DGS asset + a CUDA rasterizer on GPU).

Design choices we can justify if asked:
  - Wu et al. 4DGS chosen specifically because "freeze canonical + rigidly warp by
    physics" is essentially free with its canonical+deformation architecture.
  - We fit transformation/physics parameters instead of a network -> interpretable,
    cheap, and the whole point of the contribution.
  - No rotation applied to the object Gaussians: GT quaternions are identity for
    this non-spinning ball, so translation-only is correct here.

6. LIMITATIONS SLIDE
--------------------------------------------------------------------------------
  - Single scene / single variant shown so far; generalization across restitution
    and drop-angle variants not yet tabulated.
  - 4DGS reconstruction is a short (5k-iter) debug run -> trajectory wobble; not
    yet the 30k production quality.
  - Scene rebuild (Step 5) is currently a 2D overlay, so PSNR/SSIM are not
    representative of the eventual photoreal composite; background 3DGS missing.
  - Frame rate is a temporary 120 FPS scaffold (M2 noted intent to drop to 30/60).
  - Rigid-sphere assumption; collision/stacking/deformable generalization untested.

APPENDIX A — "IDEAL IMPLEMENTATION": what is missing and exactly how to get it
================================================================================
The wu-pred branch already contains the ideal Step 5 renderer (run_step5 in
src/phys4d/bounce/render_compose.py): it translates the canonical OBJECT
Gaussians by (p_pred - p_ref), merges them with a background Gaussian PLY, and
rasterizes via the Wu CUDA renderer (render_merged_ply_wu, stage="coarse" so the
deformation field is NOT re-applied -> no double motion). gaussian_ply.py provides
load/translate/merge/save helpers. So the CODE for the ideal path exists; the gaps
are ASSETS and COMPUTE:

  GAP 1 — Background 3DGS asset (MISSING).
    There is no background_3dgs/background.ply for this scene. Train a static
    3DGS of the room using the inverted ball mask (multi-view), or a single frame
    with the ball out of view. (Modal: train_gs / graphdeco 3DGS at /opt/gs.)

  GAP 2 — Object canonical PLY (HAVE IT).
    The Wu run is object-only ("..._wu_object"); canonical PLY is at
    .../4dgs_wu/..._wu_object/.../point_cloud/iteration_5000/point_cloud.ply
    plus deformation.pth and cfg_args. (Consider re-training to iteration_30000.)

  GAP 3 — CUDA rasterizer (NEEDS GPU).
    diff_gaussian_rasterization is NOT importable locally and this Mac has no
    CUDA. Step 5 must run on Modal (A10G). The Wu submodules
    (depth-diff-gaussian-rasterization, simple-knn) must be initialized/built in
    the GPU image. Without it, run_step5 falls back to the 2D overlay (current).

  GAP 4 — Wire it end-to-end with the stepN scripts.
    The big-ball results currently live under the older fudan "phaseN" output
    layout. The wu-pred milestone3 scripts are step4a_extract / step4b_fit /
    step4c_predict / step5_render / step6_eval. The existing predicted trajectory
    CSV is reusable; mainly need step5_render (on GPU, with --bg-ply and
    --cfg-args) then step6_eval for PSNR/SSIM.

  Command sketch for the real render (run on Modal GPU):
    python scripts/bounce/step5_render.py \
      --canonical <.../point_cloud/iteration_30000/point_cloud.ply> \
      --bg-ply    <.../background_3dgs/background.ply> \
      --predicted <OUT>/step4c/trajectory_predicted.csv \
      --ref-traj  <OUT>/step4a/trajectory_smoothed.csv \
      --dynerf-export <EXPORT_with_transforms_test.json> \
      --cfg-args  <.../cfg_args> \
      --out <OUT>/step5
    python scripts/bounce/step6_eval.py \
      --predicted ... --gt-poses ... --rendered <OUT>/step5/renders \
      --gt-rgb-root <SCENE>/rgb --out <OUT>/step6
